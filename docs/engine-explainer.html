The one asymmetry to keep in your head Prefill is compute-bound. Decode is memory-bound. They need opposite fixes, and mixing them up has cost this project real money. Prefill already scales — server-instrumented prefill rises 4.8× from B=1 to B=64 [measured]. Decode does not, and every hard problem below is a decode problem. Batching is the one lever that turns decode's memory-bound shape into prefill's compute-bound shape — which is why aggregate throughput and per-user throughput pull in opposite directions, and why you must always say which one you mean.

Sources. Every number traces to memory/mission/CEILINGS.json (physics bounds and the anti-pessimism protocol), memory/mission/FACTS.md (hardware-measured only, with provenance and retractions) and docs/BENCHMARKS.md. [measured] = ran on real hardware. [physics] = a bound reality imposes, derived from bytes and bandwidth. [projected] = arithmetic, not yet run. [measured-by-design] = the byte accounting is exact and verified in source, but the path has not executed on a GPU.

House rule, and it is the important one: a measured number describes today's code. It is never evidence about what is possible. Only physics bounds what is possible. Quote the gap and the bound in the same breath, so a bad number reads as work to do rather than as a verdict.

No competitor benchmarks appear on this page that we have not run ourselves. Where a reference project's own published figure is cited — the 90.8 8-shot GSM8K, the ~80%-of-peak GEMV, the 2.30 MTP acceptance floor — it is labelled as theirs, and as unverified by us.
